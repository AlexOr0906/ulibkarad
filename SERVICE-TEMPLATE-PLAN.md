## Предлагаемая композиция и API, подлежащие сверке с handoff

Контентный `ServicePageContent.astro` внутри InternalPageLayout, один article и **один h1**. Сам шаблон не создаёт второй main или копии шапки/футера. Контейнеры принадлежат шаблону; индивидуальная сцена получает свободную по ширине область, без навязанного transform/pin/высоты.

Порядок по умолчанию:

```text
хлебные крошки → название направления и честный статус демо
[scene: необязательный named slot, собственное движение A]
[описание направления]
[содержательные информационные блоки]
[подтверждённые связанные врачи]
[утверждённая стоимость]
[переход к действующему месту связи]
```

Named slot `scene` проверяется через `Astro.slots.has('scene')`. При отсутствии слота нет пустого wrapper/зарезервированного экрана. Общий reveal не оборачивает индивидуальную сцену: движение A не должно суммироваться с общим transform/mask. Конкретные имена/props/initializer сцены пока не назначены: это должен определить передаваемый контракт A.

Для русского текста — текущий Manrope, существующий Cormorant Garamond только в фирменном знаке. Крупный заголовок и читаемые текстовые колонки; структурные линии там, где они разделяют информацию, без повторения пустых карточек. Шаблон спокойнее главной, не создаёт новую длинную сцену.

## Типизированные данные: предлагаемая модель

Развести **отсутствующий блок** и **явно обозначенное демонстрационное место**. Не использовать пустые строки как признак готовности и не рендерить заголовок секции без содержимого.

```ts
type OpeningDirection =
  | 'children-therapy'
  | 'adult-therapy'
  | 'prosthodontics'
  | 'orthodontics';

type Section<T> =
  | { state: 'ready'; content: T }
  | { state: 'placeholder'; notice: string };

interface ServicePageData {
  id: OpeningDirection;
  title: string;
  breadcrumbs: readonly { label: string; href?: string }[];
  demoNotice?: string;
  description?: Section<readonly string[]>;
  information?: readonly ServiceInfoBlock[];
  relatedDoctors?: Section<readonly ApprovedDoctorReference[]>;
  pricing?: Section<ApprovedPriceList>;
  appointment?: { label: string; href: string; notice?: string };
}
```

Это эскиз типов, не код проекта и не окончательный договор с контентом A. Конкретные структуры информационных блоков/стоимости/ссылок на врачей согласуются после handoff. В ready-блоках нужны содержательные массивы; пустой массив/неразрешившиеся doctor references не создают секцию. Готовые цены допускаются только из материалов клиники; placeholder не содержит суммы или обещания «от …».

Врачей разрешать по подтверждённым данным, с реальной существующей ссылкой/поддержанным профилем. Если их ещё нет — не выбирать случайные демонстрационные карточки. Прототип при необходимости показывает явно подписанное место, а не сотрудника.

Назначение CTA до готовой записи — существующий блок связи. Не делать вид, что заявка отправляется. Поле appointment опционально: нет корректного места связи — нет активной кнопки-заглушки.
